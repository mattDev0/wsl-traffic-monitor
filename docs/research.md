# WSL Traffic Monitor Research

Status: initial technical investigation  
Date: 2026-07-18  
Scope: native Windows application for measuring network traffic generated by WSL2 only

## Executive Summary

The lowest-overhead MVP should measure WSL2 traffic by polling Windows interface counters for the WSL-owned virtual network path, using the IP Helper API (`GetIfTable2` / `GetIfEntry2`) and conservative adapter discovery. This is accurate and cheap in classic WSL2 NAT mode when the WSL virtual adapter is visible and its byte counters move only for WSL VM traffic. It is not guaranteed to isolate WSL in mirrored networking mode, where WSL mirrors Windows interfaces into Linux and traffic may not be represented by one stable `vEthernet (WSL)` host interface.

Per-distribution traffic is not available from Windows interface counters. Microsoft documents that WSL2 distributions share the same WSL2 VM network namespace, so Windows sees one VM/network stack rather than independent per-distro network interfaces. Per-distro attribution likely requires an in-guest Linux agent or cooperation from WSL internals that are not documented as public APIs.

Per-process traffic inside WSL is technically possible, but not as a zero-permission host-only feature. It requires Linux-side observation such as `/proc`, `nftables`, cgroup accounting, eBPF, or packet capture inside the WSL VM. That introduces privilege, distro integration, overhead, and trust-boundary concerns. It should be a later optional feature.

Docker Desktop must be treated as a first-class interference source. Docker's current Windows documentation says Docker Desktop on WSL2 routes container networking through `com.docker.backend.exe` on the host, while also using its own `docker-desktop` WSL distribution. Depending on what the user means by "WSL traffic", Docker traffic may need to be included, excluded, or reported separately.

Recommended direction:

- MVP: host-only interface-counter monitoring for WSL NAT mode.
- v0.2: robust detection of WSL networking mode, Docker Desktop state, adapter identity, and confidence level.
- v0.3+: optional ETW/WFP experiments for attribution and validation.
- v1.0: stable tray/taskbar UI, history, diagnostics, and clearly labeled accuracy modes.

## Technical Findings

### 1. How WSL2 Networking Works Internally

Verified facts:

- WSL2 runs a real Linux kernel inside a lightweight utility VM.
- WSL2 distributions share one network namespace in that VM.
- In default NAT mode, WSL2 uses a NAT-based architecture. The Windows host and WSL guest commonly communicate through private addresses, for example a WSL guest IP and a Windows host gateway IP visible from `ip route`.
- WSL2 networking is managed by Windows/WSL and can be affected by Windows Firewall, Hyper-V firewall, VPN clients, DNS tunneling, proxy mirroring, and WSL configuration.

Likely assumptions:

- In NAT mode, the useful host-side measurement point is the WSL virtual Ethernet path. On many machines this appears as a `vEthernet (WSL)` or similarly described Hyper-V virtual Ethernet adapter.
- Adapter names are not a stable API. Discovery should combine interface description, LUID/index, network profile, addresses/routes, WSL state, and observed counter movement.

Unknowns requiring experimentation:

- Exact adapter naming and counter behavior across Windows 10, Windows 11, Store WSL versions, NAT fallback to VirtioProxy, corporate VPNs, and Hyper-V feature combinations.
- Whether WSL Store versions after 2.3.25 expose different host counters when NAT falls back to VirtioProxy.

### 2. NAT Mode vs Mirrored Networking

Verified facts:

- WSL uses NAT mode by default.
- Mirrored mode is available on Windows 11 22H2 and higher.
- Mirrored mode mirrors Windows network interfaces into Linux and is intended to improve VPN compatibility, IPv6 support, multicast support, localhost behavior, and LAN access.
- DNS tunneling answers DNS requests from WSL using a virtualization feature rather than normal network packets.
- Current WSL configuration recognizes `none`, `nat`, `bridged` (deprecated), `mirrored`, and `virtioproxy`.

Implications:

- NAT mode has a clearer VM boundary and is better suited to low-overhead host-side byte counting.
- Mirrored mode is better for user networking compatibility but worse for simple "one virtual adapter equals WSL traffic" accounting.
- DNS tunneling may reduce observable DNS packets, so packet counters will not necessarily match user expectations for all network activity.

Unknowns requiring experimentation:

- Whether mirrored mode exposes reliable per-WSL counters through any Hyper-V, HNS, WFP, ETW, or interface object.
- Whether a native app can classify mirrored-mode WSL packets without a driver or privileged WFP callout.

### 3. Hyper-V Virtual Switches and Adapters

Verified facts:

- Hyper-V NAT uses an internal virtual switch to give VMs network access via the host.
- Hyper-V virtual switches run in the Windows management OS and connect external adapters, internal host adapters, and VM network adapters.
- Hyper-V extensible switch supports NDIS filter extensions and an in-box WFP filtering extension.
- Hyper-V firewall settings apply to WSL and use WSL's VM creator ID in documented examples: `{40E0AC32-46A5-438A-A0B2-2B479E8F2E90}`.

Likely assumptions:

- WSL NAT traffic crosses a Hyper-V/Host Networking Service managed path whose counters are surfaced as one or more Windows network interfaces.
- Hyper-V switch extension APIs could observe WSL more precisely, but would require driver-level work and signing.

Unknowns requiring experimentation:

- Whether WSL's hidden/managed switch is exposed through stable WMI or Hyper-V APIs on all supported client SKUs.
- Whether Hyper-V port counters can be retrieved for the WSL VM without admin rights.

### 4. Windows APIs for Interface Statistics

Verified facts:

- `GetIfTable2` returns a MIB-II interface table containing `MIB_IF_ROW2` entries.
- `MIB_IF_ROW2` exposes byte counters such as `InOctets`, `OutOctets`, unicast/multicast/broadcast octets, packet counts, discards, and errors.
- `GetIfEntry2` retrieves details for one interface identified by interface LUID or index.
- These APIs are available since Windows Vista and are suitable for desktop applications.

Assessment:

- These APIs are the best MVP polling mechanism because they are stable, low overhead, do not require packet capture drivers, and avoid elevated privileges for normal reads.
- They measure interface bytes, not semantic ownership. Correctness depends on selecting the right WSL-only interface.

### 5. APIs for Packet Counters and Attribution

Verified facts:

- `MIB_IF_ROW2` includes packet counters at interface scope.
- IP Helper can enumerate TCP endpoints with owning PID using `GetExtendedTcpTable`, but endpoint ownership is not byte accounting.
- TCP extended statistics can report bytes for a TCP connection through `GetPerTcpConnectionEStats`, after extended statistics are enabled. It does not cover UDP/ICMP and excludes protocol headers.
- ETW TCP/IP events can trace network activity with process information, but Microsoft notes process/thread identity caveats for some events.
- WFP ALE layers classify traffic per connection/socket and can filter based on application identity and user identity. Non-ALE layers classify per packet.
- Hyper-V extensible switch extensions and WFP callouts can inspect or filter switch traffic, but that is driver/security-sensitive territory.

Likely assumptions:

- ETW can be useful for diagnostics and validation, not as the first production accounting path.
- WFP or a Hyper-V switch extension could be the most precise Windows-side architecture, but likely violates the lightweight/no-admin goal and increases signing, compatibility, and support costs.

Unknowns requiring experimentation:

- Whether ETW TCP/IP events include enough WSL VM identity in NAT and mirrored mode to isolate WSL without packet capture.
- Whether WFP layers can identify WSL traffic by compartment, virtual switch metadata, package/creator ID, or interface in user mode.

### 6. Can WSL Traffic Be Distinguished From Normal Windows Traffic?

Verified facts:

- In NAT mode, WSL traffic is separated by the VM networking path.
- In mirrored mode, WSL intentionally shares/mirrors Windows network interface topology into Linux.
- WSL2 distributions share one network namespace, so host-side per-distro separation is not naturally available.

Assessment:

- NAT mode: yes, likely distinguishable with high confidence by WSL virtual adapter counters.
- Mirrored mode: unknown. A simple host physical adapter counter cannot separate WSL from Windows processes.
- VirtioProxy fallback: unknown. Needs targeted tests.

Recommended product behavior:

- Report a confidence level: `High` for validated WSL NAT interface, `Experimental` for mirrored/VirtioProxy, `Unsupported` when no reliable isolation point is found.
- Never silently show total host traffic as "WSL traffic".

### 7. Docker Desktop Interference

Verified facts:

- Docker Desktop can run with a WSL2 backend.
- Docker Desktop uses a `docker-desktop` WSL distribution and optional integration with user distros.
- Docker documentation says Windows container/VM network operations are routed through `com.docker.backend.exe`; outbound container traffic originates from this host process from the perspective of firewalls/security tooling.
- Microsoft documents known Docker container issues with WSL mirrored networking and published ports.

Implications:

- Docker may inflate WSL VM counters if its WSL distribution shares or uses the same WSL VM networking path.
- Docker may bypass WSL adapter attribution if traffic is proxied through `com.docker.backend.exe`.
- A WSL Traffic Monitor must explicitly detect Docker Desktop and disclose whether Docker traffic is included, excluded, or separately estimated.

Unknowns requiring experimentation:

- Counter behavior for Docker pulls, container egress, and published ports in NAT mode.
- Counter behavior for Docker Desktop with mirrored networking enabled.
- Whether Docker host-process ETW/PID attribution can reliably subtract Docker traffic from WSL adapter counters.

### 8. Per-Distribution Traffic

Verified facts:

- WSL2 distributions share the same network namespace.
- WSL2 distributions have separate PID, mount, user, cgroup, and init process namespaces.

Assessment:

- Host-only per-distro traffic is probably not technically possible with interface counters.
- In-guest per-distro attribution may be partially possible because each distribution has separate process and cgroup namespaces, but the shared network namespace means bytes are not naturally separated by NIC.

Likely approaches:

- Optional Linux agent per distro that samples per-process socket or cgroup accounting.
- Launching commands through `wsl.exe --distribution <name>` to read Linux counters, accepting startup and trust costs.
- Future integration with WSL internals if Microsoft exposes stable distro-scoped counters.

Unknowns requiring experimentation:

- Whether WSL assigns stable cgroup markers per distro that can be used by eBPF or nftables accounting.
- Whether Docker Desktop and system services blur distro attribution.

### 9. Per-Process Traffic Inside WSL

Verified facts:

- Windows APIs can attribute Windows TCP endpoints to Windows PIDs, but WSL Linux processes are not ordinary Windows socket owners.
- Linux has mechanisms for per-process/network observation, including `/proc`, cgroups, packet capture, firewall counters, and eBPF, but privilege requirements vary.

Assessment:

- Per-process WSL traffic is feasible only with an in-guest component or privileged instrumentation.
- A host-only native Windows app should not promise this for MVP.

Tradeoffs:

- `/proc` scanning: lower privilege, higher ambiguity and polling overhead.
- eBPF: high fidelity and low overhead when available, but kernel capability and privilege requirements are significant.
- nftables/iptables counters: useful for rule-based accounting, but modifies guest networking/firewall state.
- Packet capture: broad protocol coverage but higher overhead and permissions.

### 10. Lowest-Overhead Accurate Architecture

Best candidate:

- Poll selected Windows interface counters with `GetIfEntry2` every 1 second.
- Keep a previous counter snapshot and monotonic timestamp.
- Compute upload/download from unsigned deltas divided by elapsed time.
- Smooth display using a short moving average or exponential smoothing at the UI layer only.
- Re-enumerate adapters on network-change notifications or when counters disappear/reset.

Why:

- No packet capture driver.
- No kernel driver.
- No per-packet processing.
- No admin requirement for normal reads.
- Minimal allocations and CPU use.

Limitations:

- Accuracy depends on interface selection.
- Mirrored/VirtioProxy modes need separate validation.
- It measures bytes crossing an interface, not user-intent traffic categories.

### 11. Polling Interval Performance Implications

Likely assumptions:

- 1 second is the right default for tray/taskbar display: responsive enough for humans and cheap for one or a few interfaces.
- 500 ms gives smoother display but doubles API calls and UI churn.
- 2 seconds lowers overhead but feels laggy and misses short bursts.
- 5 seconds is appropriate for history aggregation, not live display.

Recommended:

- Poll raw counters at 1 second while visible/active.
- Drop to 2-5 seconds when only collecting history or on battery saver.
- Avoid polling all interfaces every tick after the WSL interface has been identified; poll the selected interface by LUID and periodically validate identity.

Unknowns requiring experimentation:

- CPU and wakeup impact on low-end laptops.
- Counter update granularity for WSL virtual adapters.
- Impact of `GetIfTable2` full enumeration versus `GetIfEntry2` single-interface polling.

### 12. Required Windows Versions

Verified facts:

- `GetIfTable2` / `GetIfEntry2` are available since Windows Vista.
- WSL2 requires supported Windows 10/11 builds; Microsoft Store WSL has its own versioning.
- Mirrored networking requires Windows 11 version 22H2 or higher.
- WSL firewall integration requires Windows 11 22H2 and WSL 2.0.9 or later.
- Advanced `.wslconfig` networking settings require Windows 11 22H2 or higher.

Recommended support matrix:

- MVP target: Windows 10 and Windows 11 with WSL2 NAT mode.
- Full fidelity target: Windows 11 22H2+ with WSL 2.0.9+, after mirrored/VirtioProxy experiments.
- WSL1: out of scope unless explicitly added later, because it does not use the WSL2 VM network boundary.

### 13. Required Permissions

Likely permission model:

- Interface counter polling: standard user.
- Enumerating WSL distros through `wsl.exe -l -v`: standard user.
- Reading `.wslconfig`: standard user for current user's configuration.
- ETW real-time kernel network tracing: may require administrator or special trace privileges depending on provider/session.
- WFP callouts, Hyper-V switch extensions, packet capture drivers: admin/install/signing.
- In-guest eBPF or firewall accounting: root or Linux capabilities inside WSL.

Unknowns requiring experimentation:

- Whether all needed adapter metadata is available to non-admin users on locked-down enterprise machines.
- Whether Hyper-V firewall and HNS state inspection can be done without admin.

### 14. Edge Cases and Failure Scenarios

- WSL is not installed.
- WSL is installed but no WSL2 distros exist.
- Only WSL1 distros exist.
- WSL VM is stopped; virtual adapter may not exist or counters may be zero.
- WSL starts/stops while the app is running.
- Adapter LUID/index changes after `wsl --shutdown`, reboot, network reset, or Windows update.
- WSL NAT falls back to VirtioProxy.
- Mirrored networking is enabled.
- User has deprecated bridged mode configured.
- User has `networkingMode=none`.
- VPN changes routes or blocks WSL NAT.
- DNS tunneling causes DNS traffic not to appear as packets.
- Docker Desktop is running and generating WSL/container traffic.
- Corporate firewall policy disables local rule merging or blocks WSL.
- IPv6 is disabled in a way that breaks WSL connectivity.
- Hyper-V is disabled or unavailable.
- Counters reset, wrap, or jump backwards after adapter recreation.
- Multiple virtual adapters match WSL-like names.
- Localization changes adapter names.
- User renames adapters.
- Sleep/resume creates large elapsed-time gaps.
- System clock changes; use monotonic time for deltas.
- Very high throughput creates UI formatting and history aggregation pressure.

### 15. Existing Open-Source Projects

TrafficMonitor:

- Windows network-speed floating/taskbar monitor.
- Strong UI precedent: floating window, taskbar display, skins, history, plugin system.
- Weakness for this product: general host network monitoring, not WSL-specific isolation.
- Source: https://github.com/zhongyang219/TrafficMonitor

NetSpeedTray:

- Lightweight open-source Windows taskbar network monitor.
- Strong precedent for native taskbar integration and efficient display.
- Weakness for this product: general network speed, not WSL-specific accounting.
- Source: https://github.com/erez-c137/NetSpeedTray

RustNet:

- Cross-platform Rust network monitor with interface stats, per-process attribution, DPI, packet capture, and Windows `GetIfTable2` usage.
- Strong precedent for Rust architecture and multi-platform network observation.
- Weakness for this product: much broader scope, packet capture dependency on Windows, and not WSL-specific.
- Source: https://github.com/domcyrus/rustnet

network-speed crate:

- Rust crate focused on Windows interface speed monitoring.
- Strong precedent for interface-counter API ergonomics.
- Weakness for this product: adapter filtering defaults often exclude virtual adapters, while this product must intentionally target a WSL virtual path.
- Source: https://docs.rs/network-speed

psnet:

- Rust Windows TUI network monitor.
- Strong precedent for Rust-based live network display without Npcap for basic UI.
- Weakness for this product: TUI/general network monitor, not tray/taskbar WSL-specific.
- Source: https://docs.rs/crate/psnet

## Recommended Experiments

1. NAT adapter identity matrix:
   - Windows 10 + inbox WSL.
   - Windows 10 + Store WSL.
   - Windows 11 pre-22H2 if available.
   - Windows 11 22H2+ with current WSL.

2. Counter validation:
   - Idle WSL.
   - `curl`/`wget` inside one distro.
   - simultaneous Windows host download.
   - simultaneous WSL and Windows traffic.
   - compare selected interface deltas against Linux `/proc/net/dev`.

3. Mirrored mode:
   - enumerate host interfaces before/after enabling mirrored mode.
   - generate WSL-only traffic and identify which Windows counters move.
   - repeat with Windows host traffic on same physical NIC.

4. Docker Desktop:
   - Docker Desktop idle.
   - `docker pull`.
   - container outbound download.
   - container published port inbound/outbound.
   - WSL integration enabled/disabled per distro.

5. Permission audit:
   - standard user vs administrator.
   - enterprise firewall/group policy if available.
   - ETW kernel trace privilege requirements.

6. Polling overhead:
   - `GetIfTable2` all interfaces vs `GetIfEntry2` selected interface.
   - 250 ms, 500 ms, 1 s, 2 s, 5 s intervals.
   - CPU, memory, wakeups, and UI latency.

## Research Conclusions

Verified:

- Host interface counters are the correct first measurement primitive.
- WSL2 distros share one network namespace, which blocks easy host-only per-distro attribution.
- Mirrored networking changes the accounting problem materially.
- Docker Desktop can distort the meaning of "WSL traffic".

Likely:

- NAT mode can be monitored accurately enough for MVP with adapter counters.
- Mirrored mode will require either reduced confidence, extra attribution, or an unsupported label.
- Per-process and per-distro features require a Linux-side component or privileged instrumentation.

Unknown:

- Stable mirrored-mode attribution.
- VirtioProxy counter behavior.
- Docker subtraction/inclusion semantics that match user expectations.
- Non-admin availability of Hyper-V/HNS metadata needed for robust detection.
